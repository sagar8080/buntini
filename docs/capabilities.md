# Buntini capability and evidence map

Reviewed against the source on October 22, 2026. The raw Apple multi-step model gate remains **failed**. Controller-protected journeys are measured separately in the [evaluation evidence](evaluations.md). “Implemented” means an executable code path exists. Automated tests exercise validation, parsing and failure handling; they do not establish that a permission prompt, third-party app or live provider works on every Mac. See [device/provider acceptance](acceptance.md#remaining-interactive-sequence) for the checks still required before making reliability claims.

## Boundaries that shape useful work

- A model-driven task has at most 12 recorded steps. Its goal, model messages, step inputs, approvals, evidence and receipts persist. Approval resumes the same task; after restart, pending approvals remain and interrupted reads pause. No action is automatically repeated after an interrupted dispatch. The controller stops after failed prerequisites and requires an explicit user action request before showing a mutation proposal. Ambiguous English or other languages may require additional details. This is not proof of arbitrary goal completion.
- Planning offers only the next unfinished user-requested write, after successful prerequisite reads. Completed write obligations disappear from subsequent tool menus. Supported action-only tasks finish directly from verified receipts. Failed reads can be explicitly retried without replaying earlier writes. Failed or unknown writes cannot be resumed automatically.
- One explicitly named note with `with body`, optionally followed by one exact reminder, binds literal fields without model inference. Quoted bodies preserve embedded commands and line breaks. Other separated clauses, conflicting guidance or ambiguous fields require a new, complete request.
- One explicitly named reminder followed by `due` and an exact timestamp binds its title and due field directly from the user's instruction, across all brains. Quoted title text stays literal; incomplete or ambiguous fields are refused. The narrow grammar does not infer relative dates, multiple reminders or conflicting later clarifications.
- The exact question “What is my first calendar event on YYYY-MM-DD?” uses complete typed evidence to select and display the earliest timed event; empty complete data reports no events. Partial, tied, all-day or invalid data is refused. Extra questions use the regular planner.
- A preparation reminder for the first event on one explicit `YYYY-MM-DD` can be bound to complete structured Calendar evidence and a single minute/hour offset. The runtime selects the earliest event, calculates the due time across midnight/daylight-saving changes, preserves source timestamps with UTC offsets and carries its source through approval and the receipt. Empty, partial, tied, all-day or unsupported event selections pause for clarification; general natural-language scheduling is not proven reliable.
- AppleScript writes return typed succeeded/failed/unknown receipts. Reminders, Calendar, Notes and Mail drafts retain stable destination identifiers and read back their created fields; timeouts/mismatches stop the task as unknown. Approval IDs prevent replay of a dispatched intent, but independently submitting the same request is a new intent. There are no cross-app transactions or automatic rollbacks. Music and tab workflows verify selected state; named Spotify search and Arc tab switching are not supported in the approved multi-step path. Direct deterministic skills remain separate.
- Timers and monitor schedules/results persist, but delivery and checks depend on Buntini running and the Mac being awake. Closing the window keeps it running; quitting stops it. Overdue work runs once on return, with lateness recorded. There is no OS background helper, wake alarm, delivery-time guarantee or replay of every missed interval. Desktop notification acceptance does not prove the person saw the alert; failed/unknown attempts remain inspectable.
- The approved browser workspace reads bounded page text in an isolated persistent per-origin profile on macOS 14+. It verifies its profile/network boundary before navigating and blocks cross-origin navigation, popups and downloads. Manual sign-in may work; OAuth redirects can be blocked. It does not attest that login or website actions succeeded. Live authenticated-site acceptance is outstanding. There is no general website operator: no arbitrary form filling, authenticated booking, checkout, purchase, external message sending, account changes or arbitrary shell commands. Opening Docs, Gmail or a booking site is navigation, not a document/email/booking integration. There is no dedicated document-generation/export workflow.

## Release acceptance priorities

Use disposable records/accounts for the [interactive sequence](acceptance.md#remaining-interactive-sequence). Verify one complete success, cancellation, permission-denial and retry path for each enabled integration. Prioritize calendar/reminder date correctness, duplicate handling after uncertain action completion, browser foreground/private context, Spotify recording match, monitor pause/delete during a check, and sleep/restart notification delivery. Record destination evidence and timing with the exact packaged revision; fixture passes alone do not establish real-life task success.
